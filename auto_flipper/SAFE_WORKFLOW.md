# Контролируемый цикл перепродажи

Эта версия добавляет наблюдение, ручную проверку кандидатов, реальный допуск по EV и лимитам, журнал платежей и отдельную приёмку. Она подготовлена для проверки в симуляции и работы с подтверждёнными ручными данными. Прибыльность ассортимента и полный автоматический цикл на реальном FunPay пока не подтверждены.

## Что изменилось

- `OBSERVE` собирает кандидатов при выключенном автовыкупе. Выдача, публикация и поднятие из движка в этом режиме запрещены. Перед HTTP-записью клиент повторно проверяет режим.
- Управление доступно только положительным Telegram ID из `ADMIN_IDS`. Старые записи `is_admin` и первый посетитель не дают доступ автоматически.
- Для допуска нужны конкретный SKU, источник проверки, группа поставщика, подтверждённая передача, сумма продавцу и явно заданные вероятности/расходы. Неизвестные данные не заменяются хорошим рейтингом или предполагаемой вероятностью продажи.
- В расчёт включён отдельный исход брака при приёмке. Используются Decimal, оба порога прибыли/ROI, округление максимальной закупки вниз. Недостижимая вероятность продажи не обрезается до 100%.
- Запись покупки резервируется через `BEGIN IMMEDIATE`; одновременно разрешён один незавершённый checkout на базу. Одна и та же позиция не оплачивается повторно автоматически, в том числе после отказа.
- `pending`, `unknown` и `executed` без завершённой складской записи блокируют следующие покупки. Инвентарь, списание в копейках и завершение интента фиксируются одной транзакцией.
- Реквизиты из чата переводят реальный товар в `awaiting_intake`. Проверка формата не разрешает публикацию. Автоматические шаблоны применяются только к симуляциям; реальная публикация получает отдельно проверенный текст.
- Выдача требует точного offer ID и записи приёмки; симуляционный товар не выдаётся реальному заказу. Неопределённая отправка сохраняет резерв и связь с покупателем.
- Доставка переводит товар в `delivered` с нулевой реализованной прибылью. `/settle`, `/refund`, `/expense` учитывают подтверждённые денежные события без повторного списания закупки. Повтор одного event ID не меняет результат; конфликтующий повтор отклоняется.
- P&L исключает симуляции и старые продажи без денежных подтверждений. Срок достижения денежной цели больше не выводится из выдуманной прибыли/скорости оборота.
- Экстренный стоп ожидает ответы деактивации и показывает количество неподтверждённых снятий. `/resume` при незавершённых платежах оставляет паузу; после сверки включает OBSERVE, не восстанавливая объявления автоматически.

## Запуск

Перед запуском укажите собственный Telegram ID в `ADMIN_IDS`. Для первого прогона используйте `FLIPPER_DRY_RUN=true`, `FLIPPER_AUTO_BUY=false`, в интерфейсе выберите `OBSERVE`. Переключение DRY RUN переводит режим в наблюдение; перед реальными действиями режим выбирается явно.

Старые настройки режима хранятся в БД: перед первым запуском новой версии убедитесь, что предыдущий процесс остановлен и выбран режим наблюдения. Само наличие `LIMITED_AUTO` не обходит необходимость свежей проверки кандидата и финансовых ограничений.

При первом открытии существующей базы без новой схемы создаётся резервная копия `auto_flipper.db.pre_safe_v1.bak`; данные не удаляются и не переводятся автоматически в «подтверждённые». Копия содержит те же приватные сведения, что исходная база. Отдельная тестовая база задаётся через `FLIPPER_DB_PATH`.

Токены не помещайте в исследовательские MD или переписку. Существующие секреты и действующая конфигурация в этой доработке не перевыпускались.

## Команды нового цикла

| Команда | Действие |
|---|---|
| `/candidates` | Последние кандидаты; расчёт, причины отказа и кнопка одной покупки в ASSIST |
| `/review LOT_ID JSON` | Запись проверки кандидата и финансового снимка администратором |
| Кнопка «Подтвердить одну покупку» | Повторная проверка и один checkout; симуляция при DRY RUN |
| `/reconciliation` | Неразрешённые интенты оплаты |
| `/resolve_purchase INTENT_ID JSON` | Запись результата ручной сверки оплаты, без повторного checkout |
| `/intake ITEM_ID ИСТОЧНИК_ПРОВЕРКИ` | Подтверждение приёмки товара из `awaiting_intake` |
| `/publish ITEM_ID {"title":"…","description":"…"}` | Отдельная публикация проверенного экземпляра |
| `/bind_sale ORDER_ID OFFER_ID ИСТОЧНИК` | Точная ручная привязка заказа к объявлению, когда парсер заказа не даёт offer ID |
| `/settle ITEM_ID EVENT_ID СУММА ИСТОЧНИК` | Подтверждённое чистое поступление продавцу в рублях |
| `/refund ITEM_ID EVENT_ID СУММА ИСТОЧНИК` | Фактическое списание возврата, после сверки исходного поступления |
| `/expense ITEM_ID EVENT_ID СУММА ИСТОЧНИК` | Прямой расход на товар в рублях |

Используйте идентификатор реального денежного события как EVENT_ID. Разные команды с одним EVENT_ID не могут учитывать различные суммы. Для неизвестного результата доставки товар остаётся зарезервированным: произвольный повтор выдачи и освобождение товара не предусмотрены. Этот случай требует отдельной сверки; автоматический повтор будет добавлен только с подтверждением результата прежней отправки.

Проверка кандидата и его наблюдение действуют 60 секунд. Изменение наблюдаемых характеристик сбрасывает проверку. Любое денежное событие после проверки требует обновления финансового снимка. Это консервативный режим первого пилота, а не автоматическая калибровка рынка.

## Формат проверки

Содержимое `review_example.json` — исключительно сценарий для DRY RUN. В реальную покупку нельзя переносить его вероятности, капитал или флаги проверки без собственных оснований.

`net_receipt` — чистая сумма продавцу в рублях. Для неё используется `price_basis="seller_net"`; дополнительная процентная комиссия из старого каталога не вычитается. Цена наблюдаемого объявления не доказывает сумму реального checkout.

`model` задаёт вероятность продажи после приёмки, условный ранний дефект после продажи, поздний возврат, денежные возмещения, ликвидацию, расходы и отдельную ветку неуспешной приёмки. `late_fine`, если не задан, равен `net_receipt`. Рейтинг продавца не превращается в эти вероятности.

Денежные поля `financial` — **целые копейки**, не рубли. `available_cash` уже исключает недоступный остаток. Обязательства вычитаются отдельно только если ещё не списаны из доступного кэша. `conservative_equity` учитывает уценки и обязательства, `session_opening_equity` остаётся фиксированной базой текущей сессии. Экспозиции поставщика/категории должны включать открытые обязательства, включая риск поздних претензий.

Финансовый снимок сейчас подтверждается оператором. `supplier_group` сохраняется в проверке, но агрегатор связанных поставщиков и автоматическая сверка полного баланса ещё не реализованы. Нельзя включать автономную торговлю на основании ручного снимка, который не включает весь существующий склад и обязательства.

Примеры ручной сверки оплаты:

```text
/resolve_purchase INTENT_ID {"outcome":"paid","order_id":"ACTUAL_ORDER_ID","debit":705.00,"source":"Проверены заказ и списание по выписке"}
/resolve_purchase INTENT_ID {"outcome":"not_paid","source":"Проверены история покупок и отсутствие списания"}
```

При известном order ID сброс в `not_paid` запрещён: отмену/возврат требуется учитывать отдельным денежным событием. Старые интенты без доказательства среды DRY RUN/LIVE требуют отдельной миграции, а не автоматического приписывания им среды.

## Что ещё требуется до реального автопилота

1. Подтвердить на сохранённых обезличенных страницах FunPay способ извлечения точной суммы checkout. Сейчас `FunPayClient.checkout_quote_validator` отсутствует по умолчанию и **блокирует реальную покупку до отправки POST**. Подставлять туда цену объявления как «подтверждённый debit» нельзя.
   Даже после подключения проверки котировки реальный ответ с order ID остаётся в `executed` до `/resolve_purchase` с фактическим списанием: текущий HTTP-адаптер возвращает запрошенную цену, а не банковское подтверждение суммы.
2. Проверить реальные ответы публикации, снятия и доставки; завершить автоматическую сверку исхода запросов и входящих заказов. HTTP-транспорт существующего проекта пока не подтверждён интеграционным прогоном на площадке.
3. Добавить автоматический журнал доступных средств и обязательств, историю цен точных SKU, ограничения групп поставщиков, завершённую обработку претензий и неизвестной доставки. Текущие лимиты применяются к предоставленному снимку.
4. Провести полный ручной пилот одного сегмента и измерить прибыль после расходов/возвратов, время освобождения денег и долю брака. Программные тесты не доказывают эти показатели.

## Проверки и откат

`run_flipper_checks.py` запускает основной набор Auto-Flipper, новые сценарии потерь и математические модели на временных базах. Внешние сетевые соединения запрещены; служебные loopback-сокеты Windows asyncio разрешены. Скрипт возвращает ненулевой код при провале.

В текущем окружении установленные библиотеки в `.venv` предназначены для Python 3.13. Команда из корня проекта:

```powershell
$env:PYTHONPATH = Join-Path (Get-Location) '.venv\Lib\site-packages'
& 'C:\Users\Happy\AppData\Local\Programs\Python\Python313\python.exe' -B run_flipper_checks.py
```

Исходные файлы `auto_flipper/*.py` и `test_auto_flipper.py` перед доработкой сохранены в `CODEX_HANDOFF/backups/2026-09-12-safe-cycle`. Новые дополнительные модули перечислены рядом с этой инструкцией. Реальные покупки, публикации и выдача во время разработки не выполнялись.
