# Целевая архитектура и состояния торговли

## Текущее состояние

Аналитические модели не управляют площадкой. Рабочий процесс находится в `auto_flipper`; его существенные расхождения с документацией перечислены в разделе 11 [исследования](../research/RESEARCH_REPORT.md). Описанные ниже состояния — целевая спецификация, не отчёт о внедрении.

## Разделение процессов

Сканирование формирует наблюдения. Скоринг создаёт решение с причинами. Закупщик выполняет только подтверждённые намерения. Склад хранит конкретные экземпляры товара. Исполнитель выдачи связывает заказ с экземпляром. Отдельная сверка фиксирует расчёт, возвраты и доступность денег.

Одна глобальная переменная состояния недостаточна: десятки товаров одновременно могут находиться в разных фазах.

## Состояния экземпляра и заказа

DISCOVERED → EVALUATED → PURCHASE_PENDING → PURCHASED → VERIFIED → LISTED → RESERVED → DELIVERED → CONFIRMED → SETTLED_HOLD → AVAILABLE.

Исключения: PURCHASE_UNKNOWN, INVALID, DISPUTED, REFUNDED, EXPIRED.

| Переход | Необходимое доказательство |
|---|---|
| PURCHASE_PENDING → PURCHASED | Реальный ID заказа и проверенное списание |
| PURCHASED → VERIFIED | Проверка содержимого и условий товара |
| VERIFIED → LISTED | Реальный ID оффера и чтение его текущего состояния |
| LISTED → RESERVED | Атомарная привязка покупательского заказа к SKU/экземпляру |
| RESERVED → DELIVERED | Подтверждение отправки данных в правильный заказ |
| DELIVERED → CONFIRMED | Состояние заказа на площадке |
| CONFIRMED → SETTLED_HOLD | Реальное начисление с ценовой базой |
| SETTLED_HOLD → AVAILABLE | Проверка разрешённой суммы покупки/вывода |

Regex подтверждает формат, но не работоспособность товара. Отправка сообщения не является расчётом. Заполнение локального статуса не подтверждает состояние оффера на сайте.

## Неопределённые результаты

При timeout после покупки записывается PURCHASE_UNKNOWN. Перед повтором требуется сверить существование заказа: повторная отправка может списать деньги второй раз. Идентификатор намерения и уникальность внешнего ID обязательны.

Выдача одного экземпляра двум заказам предотвращается транзакционной резервацией, а не только проверкой уже завершённых доставок. Если точное соответствие оффера неизвестно, выдача по одной категории запрещается.

## Telegram-команды

`/status`: доступные деньги, холд, незавершённые расчёты, склад, прибыль, проблемы сверки.

`/goal`: выбранная метрика цели; без достаточной истории ETA неизвестен.

`/browser`: состояние авторизации и качество определения баланса. При неизвестном балансе нельзя подставлять бюджет как доступные деньги.

`/boost`: результат фактического поднятия и полученный срок следующей попытки. Не обещать гарантированных просмотров или продаж.

`/emergency_stop`: немедленно закрыть новые закупки, остановить связанные намерения, снять офферы с проверкой результата. Обязательства по уже оплаченным заказам остаются видимыми.

`/resume`: сверить склад и внешние объявления, восстановить только корректные офферы, отдельно показать статус авто-выкупа. Локальная смена статуса не заменяет публикацию.

## Проверка перед закупкой

Положительный скоринг товара дополняется `risk_gate.assess_purchase`: свежий проверенный баланс, обязательства по возвратам, ожидающие списания, экспозиции и предел потерь. Обе проверки затем повторяются при атомарной записи резерва; автономная функция не защищает от конкурирующих потоков сама по себе.

Очередность внедрения и 12 сценариев отказов: [план разработки](../research/RISK_AND_DEVELOPMENT_PLAN.md).

## Приёмка реализации

Проверить на изолированных сценариях: повторную оплату после timeout, две одновременные выдачи, изменение цены, возврат после доставки, перезапуск в середине операции, частичное снятие объявлений и неизвестный баланс. Критерий — отсутствие двойного списания, двойной выдачи и выдуманной прибыли.
